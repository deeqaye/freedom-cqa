# CQA: оценка качества работы оператора (NLP-часть)

Автоматическая оценка диалога клиента с оператором Freedom Broker по 8 критериям чек-листа. На вход одна беседа (чат или звонок), на выходе по каждому критерию значение, обоснование (на русском и казахском) и номера реплик-доказательств. Итоговые баллы считает сервис.

**Итог:** `nlp/evaluator.py`, одна LLM-модель `gpt-6-luna`, один вызов на оценку плюс мини-вызов на перевод обоснований.
На DEV (65 диалогов, один прогон): **96.08 / 100** взвешенного совпадения с разметкой команды, **≈ $1.29 за 1000 оценок**, **≈ 16 с на диалог**.

---

## 1. Что делает система

```
transcript ──► preprocess ──► ОДИН вызов LLM: 8 этапов, на каждом reasoning → value → evidence_turns ──► мини-вызов перевода ──► ответ
                (IVR, удержание)        (английский промпт, 4 примера, критерии из checklist["criteria"])     (reasoning EN → RU + KK)
```

1. **Предобработка** (`_view`): в звонках меню бота помечается `bot-IVR`, а участки «клиент на удержании» (оператор советуется с коллегой, клиент этого не слышит) помечаются отдельным тегом, чтобы модель не оценивала их как диалог с клиентом. Исходные номера реплик сохраняются.
2. **Оценка по этапам.** Критерии идут в порядке от менее важного к более важному (по весу), флаг грубых нарушений в конце. На каждом этапе модель сначала пишет `reasoning` (1–2 предложения на английском с номерами реплик), затем значение и `evidence_turns`. Подробнее о порядке и правилах: `PIPELINE_STAGES.md`.
3. **Мини-промпт перевода**: каждое английское `reasoning` переводится на русский (поле `rationale`, требование контракта: 1–2 короткие фразы по-русски, в формате «Завершение — Нет. …») и на казахский (`rationale_kk`). Английский оригинал сохраняется в `rationale_en`. Лишние поля сервис в `results.json` не экспортирует.
4. **Критерии берутся из чек-листа, а не зашиты в код.** Промпт собирается из `description`, `na_condition`, `steps/step_labels`, `prompt_hint`. Для 8 стандартных критериев с неизменённой формулировкой (проверка по отпечатку текста) подставляются отлаженные правила. Любой новый или изменённый критерий получает универсальный блок, собранный только из его полей. Проверено на втором чек-листе организаторов `checklist_compliance` (другие критерии и шкала): вывод проходит валидацию.
5. **Надёжность:** потокобезопасно (нет общего изменяемого состояния), ретраи на лимиты запросов (SDK, до 6 попыток), одна повторная попытка при невалидном ответе модели, при сбое исключение (ничего не подставляется нулями). Если упал только перевод, в `rationale` остаётся английский текст.

## 2. Данные и разбиение train / dev

В DEV 65 диалогов: **60 синтетических чатов** (RU 30, KZ 15, EN 15) и **5 реальных звонков** (RU, шумное распознавание речи, 45–115 реплик, меню бота, удержание).

Синтетические чаты повторяют около 12 сценариев (тариф, пополнение, вывод и анкета, отчёт, логин, облигации, маржа, D-счёт, форма 1042-S…) на трёх языках. Дословных копий нет (максимальная схожесть реплик 0.24–0.31 по символьным n-граммам), но **утечка сценарная**: сценарий из few-shot примера повторяется в проверяемом чате. Поэтому разбиение сделано **по сценариям**, а не по чатам:

| часть | диалоги | назначение |
|---|---|---|
| **train** | 45 синтетических чатов (тарифы, пополнение, вывод/анкета, отчёты, логин, облигации) | настройка правил промпта, источник few-shot примеров |
| **val** | 15 синтетических чатов отложенных сценариев (маржа, D-счёт, поиск тикера, форма 1042-S, прочее) | проверка на новых сценариях |
| **val-real** | 5 реальных звонков | проверка на реальном шумном распознавании речи |

«Обучения» модели нет: train нужен только для правил и примеров. **В few-shot попали только 4 синтетических чата из train** (`p1-ru-003`, `p1-ru-007`, `p1-ru-022`, `p1-en-006`), реальные звонки в примерах не используются. Разбиение: `data/split.json`, скрипт `scripts/make_split.py`.

**Разметка (gold).** Диалоги размечены командой вручную. Затем я перечитал разметку по текстам и по правилам чек-листа и предложил 39 правок в 28 диалогах (23 уверенных, 10 средних, 6 спорных); команда подтвердила их, кроме одной. Разметка до и после: `gold_labels_v1.json` и `gold_labels.json`, список правок с причинами: `GOLD_REVIEW.md`. Основные ошибки в исходной разметке: «Да»/«Нет» в «Выявлении потребности», где оператор ничего не спрашивал (должно быть N/A), «Завершение = Да», когда клиент уже положил трубку, `kz-004` помечен как грубое нарушение без нарушения, ответы с оценкой 0 при верной консультации. Ниже везде указано, на какой версии разметки получено число (**v1** = исходная, **v2** = исправленная).

## 3. Метрика

**Weighted agreement (взвешенное совпадение), 0–100.** Для каждого диалога и критерия: совпало значение = 1, не совпало = 0; для двух шкал (`consultation`, `dialogue`) частичный зачёт `1 − |разница|/максимум`; N/A против значения = 0. Затем веса чек-листа (10/15/20/20/15/15/5) и усреднение по диалогам. `critical` в метрику не входит (у него нет веса), следим за ним отдельно (TP/FP/FN).
Дополнительно: **MAE итоговой оценки** (насколько итоговый балл 0–100 по ответам модели отличается от балла по разметке, считается кодом сервиса), стоимость и время.

**Уровень шума.** Один и тот же промпт, запущенный подряд 8 раз, даёт 95.17 ± 0.72 (v2); на 5 звонках ± 4–6 пунктов. Различия меньше двух стандартных отклонений между одиночными прогонами считаем случайными.

### Из чего складывается стоимость и как её снизить

Оценка диалога = основной вызов (8 этапов) + мини-вызов перевода reasoning. Цены токенов `gpt-6-luna`: вход $0.10, выход $0.50 за 1M, **выходные токены в 5 раз дороже входных**, поэтому стоимость определяется тем, сколько модель пишет.

| часть | вход, токенов | выход, токенов | $ за 1000 чатов | $ за 1000 звонков |
|---|---|---|---|---|
| основной вызов: 8 этапов с reasoning, 4 примера (замер 4.4, без перевода) | 4 974 / 6 371 | 733 / 2 275 | 0.86 | 1.77 |
| мини-вызов перевода reasoning на RU и KK | ≈ 410 | ≈ 700 | ≈ 0.37 | ≈ 0.32 |
| **итого (итоговый прогон, раздел 5)** | 5 405 / 6 859 | 1 375 / 2 810 | **1.23** | **2.09** |

Почему перевод заметно дороже, чем кажется: на вход идёт только английское reasoning (около 240 токенов, то есть ≈ 960 символов на диалог), но модель пишет **два перевода** (русский и казахский, оба токенизируются хуже английского), и этот выход оплачивается по цене выхода. Входная часть перевода стоит около $0.00004 на диалог, выходная около $0.00035. Перевод даёт примерно 30% всей стоимости оценки.

Замер самого мини-вызова на реальных reasoning (3 диалога, `gpt-6-luna`):

| вариант перевода | вход | выход | $ за диалог | $ за 1000 |
|---|---|---|---|---|
| **текущий: RU + KK, `reasoning_effort=low`** | 414 | 696 | 0.00039 | 0.39 |
| только RU (контракт требует только русский) | 391 | 360 | 0.00022 | 0.22 |
| только KK | 390 | 386 | 0.00023 | 0.23 |
| RU + KK со стандартным усилием рассуждения (для сравнения) | 414 | 1 048 (из них 319 скрытое рассуждение) | 0.00057 | 0.57 |

Что можно сделать, если нужно дешевле:
1. **Переводить только на русский** (обязательное поле `rationale`), казахский делать по запросу: перевод дешевеет на ≈ 43%, оценка в среднем выходит около **$1.1 за 1000** вместо $1.29.
2. Оставить `reasoning_effort=low` для перевода (уже включено): стандартное усилие делает перевод в 1.5 раза дороже из-за скрытых токенов рассуждения.
3. Для основного вызова режим `effort=low` дешевле на 12% (чаты) и 36% (звонки) при том же качестве (раздел 4.4), но один вызов из 390 упал, поэтому по умолчанию он выключен.

Ориентиры: DEV (65 диалогов) ≈ $0.084; PROD (10 диалогов) ≈ $0.013; 1000 диалогов ≈ $1.29. Расчёт идёт по полной цене входных токенов, скидка кэша OpenAI не учитывается, реальная цена чуть ниже. Все эксперименты из раздела 4 (около 75 гипотез и вариантов, многие с повторами) обошлись, по оценке по токенам, в порядка $15–20.

## 6. Ограничения (честно)
- Реальных звонков всего **5**: цифры по ним очень шумные (один звонок меняет метрику на 20 пунктов), выводы о реальном качестве нужно подтверждать на PROD.
- Синтетика повторяет сценарии, поэтому её метрики завышены. Правила настраивались на train, но список всех расхождений я видел целиком, поэтому val не полностью «слепой».
- Из 75 гипотез и вариантов ни одна не вышла за шум (кроме явно слабых), а «лидеры» одиночных прогонов часто случайны: при 70+ вариантах это неизбежно. Выводы опираются на повторы.
- Разметка субъективна на нескольких критериях (`discovery`, `dialogue`, `empathy`), это и определяет потолок метрики.
- Казахский перевод сделан моделью и не проверялся носителем.

## 7. Запуск и деплой
```bash
uv venv --python 3.12 .venv && uv pip install -p .venv -r requirements.txt   # в requirements.txt добавлен openai
cp .env.example .env        # вписать OPENAI_API_KEY, .env в .gitignore

.venv/bin/python -m pytest                         # тесты сервиса
```
- **Переменная ключа: `OPENAI_API_KEY`** (на Render добавить как Environment Variable). Необязательные: `NLP_MODEL` (по умолчанию `gpt-6-luna`), `OPENAI_BASE_URL`, `NLP_PRICE_IN` / `NLP_PRICE_OUT` (цены в USD за 1M токенов).
- Модель в ответе: `{"mode": "external_api", "name": "gpt-6-luna"}`, `usage.cost_usd` суммирует все вызовы (оценка, перевод, повторы).
- Зависимость `openai` добавлена в `requirements.txt` (иначе сборка на Render упадёт).
